# ponytail 감사 보고 — GoldMiner v5.5.4 (2026-07-31)

프로파일 출처 [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) (MIT, ⭐92.9k).
사다리: ①존재해야 하나(YAGNI) ②이미 있나 ③표준에 있나 ④플랫폼 기본인가 ⑤기존 의존성 ⑥한 줄로 되나 ⑦그제서야 최소 구현.

## 한 줄 결론

**미결 백로그 5건 중 새로 만들어야 하는 건 0건입니다.** 2건은 이미 코드에 있고, 1건은 MQL5 표준이 해결하고, 2건은 각각 1~2줄입니다.
그리고 아무도 못 봤던 진짜 문제가 하나 나왔습니다 — **TEST_A가 LATEST와 다른 EA라, 예정된 ARM_USD A/B가 지금 상태로는 아무것도 검증하지 못합니다.**

## A. 오늘(7/31) 추가분 — 중복인가?

의심했던 "해제선 판정이 여러 군데 중복" 은 **논리 중복 0** 으로 나왔습니다.

| 지점 | 담당 상태 | 판정 |
|---|---|---|
| 16236 레스큐 해제선 | `SnapAdd` 콜백 경로 (`LHEDGE_Update` 밖) | 유지 |
| 16307 VScan 해제선 | `setLive == true` | 유지 |
| 17394 arm 4단 | `!g_lh.active` | 유지 |
| 17515 전개 해제선 | `!done && !setLive` (VScan과 상호배타) | 유지 |

네 지점이 **서로 겹치지 않는 상태**를 담당합니다. 한 군데로 접으면(`LHEDGE_Update` 최상단 early-return) 같은 함수 안의 `LHEDGE_ComboExit`·`LHEDGE_Fire`·done 판정까지 막혀서 **출구 계통이 죽습니다.** 접기 금지.

남는 건 **텍스트 중복 3벌**(변수명만 다르고 본문 동일)뿐입니다. `LHEDGE_ReleaseHold()` 7줄로 접으면 −8줄인데, **전파 작업에 끼워서만** 값이 있습니다(전파 후엔 3파일 × 3벌 = 9벌이 되므로). 단독으로 라이브 파일 열고 F7 한 사이클 태울 값은 없습니다.

**`LHEDGE_ARM_WAIT_MIN = 0`** — 죽은 코드처럼 보이지만 삭제 반대입니다. 값 1개 + 분기 1줄이라 유지비가 0이고, 지우면 나중에 켤 때 arm 축 재수술이 필요합니다. 대신 `// ponytail:` 주석으로 "0일 때 이 단계는 무조건 통과 = 실효 1단" 을 명시해 두는 게 맞습니다. (12조합 자체점검 결과 WAIT=0에서 4단은 `if(flU <= -thrU) Arm()` 단일 조건과 **완전 동치** 확인.)

## B. 미결 백로그 — 만들 것 vs 안 만들 것

### P6 (arm·위기 모집단에서 해결사 777 제외) → **이미 되어 있습니다. 0줄.**

arm 모집단 함수 두 개가 전부 202604 전용 필터를 이미 갖고 있습니다.

```
LHEDGE_SideFloating (15802):  if(PositionGetInteger(POSITION_MAGIC) != MagicNumber) continue;
SumOpenLotsBySide   (4138):   동일 필터
```

`SOLVER_MAGIC = 777` 은 `g_solverTrade.SetExpertMagicNumber(SOLVER_MAGIC)` 로 별도 발행되므로 **모집단에 애초에 안 들어옵니다.** 위기 축 `LHEDGE_RatioFloor()` 는 가격 심도 기반이라 포지션 모집단과 무관하고요.

→ 백로그에서 내리십시오. 다만 앞서 "600029에서 777 포함 40.32로 발동" 관측이 있었다면 **다른 경로**입니다. 그 함수명을 특정해서 다시 올려야 합니다 — 근거 없이 "구현"으로 넘어가면 7전째 헛장치가 됩니다.

### IsCrisisPhase() 신설 → **이미 있습니다. 0줄.**

위기 판정은 `LHEDGE_RatioFloor() > 0.005` 이고, 주석에 "위기 국면(하한 활성)" 이라 적혀 있으며 **3지점에서 같은 의미로 쓰이고 있습니다**(16427 Fire 보류 / 17246 ComboExit 보류 / 17364). "이슈 아니면 통째" 분기는 이 식을 그대로 쓰면 됩니다. 별칭 `#define` 조차 불필요합니다 — 추가는 추가입니다.

간극 하나: `RatioFloor()` 는 `if(!g_lh.active) return 0;` 이라 **헷지 비활성 국면을 항상 평시로 봅니다.** 그것까지 덮어야 하면 `(g_ddmStageBuy > 0 || g_ddmStageSell > 0)` 로 대체 — 여전히 신규 축 0입니다.

### BUILD_DATE 고착 → **죽은 define입니다. 표준이 해결합니다.**

`BUILD_DATE` 는 706에서 정의되고 **레포 전체 참조 0회**입니다. 표시처였던 `L_BUILD` 는 사장님이 명시적으로 뺐고요(`// [v5.4.0-UI10] BUILD 표기 제거 — 판별은 파일명으로`). 즉 "20260727 고착" 이 아니라 애초에 아무 데도 안 쓰이는 상수였습니다.

MQL5가 이미 줍니다 — `__DATETIME__`(컴파일 날짜+시각), `__DATE__`, `__FILE__`, `__MQL5BUILD__`.

가장 게으른 형태: 706 죽은 define **삭제(−1줄)** + INIT 로그에 1줄:

```mql5
if(DEBUG_LEVEL>0) PrintFormat("[MOMANTIC]| INIT | BUILD %s", TimeToString(__DATETIME__, TIME_DATE|TIME_MINUTES));
```

**정미 0줄, 영구 자동 갱신, 다시는 고착 불가.** 대시보드 표기 부활은 금지입니다(사장님이 뺀 것). 718 `BUILD_VER` 에 붙이면 브랜드 헤더까지 오염되니 하지 마십시오.

### R3 (Sweep 실패 로그) → **2줄.**

`PM_OrphanSweep` 은 손댈 것 없습니다(실패해도 60초 주기 재시도 = 자기치유).

진짜 결함은 `WLU_IslandTPSweep`(17822) 한 곳입니다:

```mql5
g_wluTrade.PositionModify(g_wluTk[i], PositionGetDouble(POSITION_SL), 0);
if(WKL_LOGS) PrintFormat("[WLU][G5] 섬 TP 재소거 tk=%I64u", g_wluTk[i]);
```

반환값을 버리고 **그 다음 줄에서 무조건 성공 로그**를 찍습니다. G5는 7/27 갭 사고(락 중 TP 잔존) 재발 방지 장치인데, 영구 실패해도 저널엔 성공만 쌓입니다 = **거짓 성공 로그**. 안전 게이트의 관측성이라 깎을 수 없는 범주입니다.

수정 = 위 2줄을 `if(...) {성공로그} else if(WKL_LOGS) {실패로그 + retcode}` 로. **정미 +2줄, 신규 심볼 0.** 쿨다운·재시도 장치 추가는 금지입니다(60초 주기가 이미 담당).

### 3상태 버튼 렌더 → **1줄. 앤트가드는 0줄.**

렌더러 `RailButton` 은 **이미 3상태**입니다(`RSTATE_OFF/READY/ON` + 색 4분기). 고칠 게 없습니다.

결함은 호출부 1줄, 15772:

```mql5
RailButton("BTN_PM_START", 2, "PM START", running ? RSTATE_OFF : RSTATE_READY);
```

B1(7/30)이 핸들러는 3분기로 고쳤는데 렌더 호출은 `running` 만 봅니다. 라벨을 `(running && g_pm_softClose) ? "PM RESUME" : "PM START"`, 상태를 `(running && !g_pm_softClose) ? RSTATE_OFF : RSTATE_READY` 로 바꾸면 끝입니다. 신규 함수·상수 0.

**앤트가드는 이미 3상태입니다**(`BOOSTER OFF` / `BOOSTER CLOSING...` / `BOOSTER ON`). GM만 1줄.

## C. ⚠ 진짜 발견 — TEST_A가 LATEST와 다른 EA입니다

GOLD_INDEX §4-3 "TEST_A로 ARM_USD A/B 1런" 은 **지금 상태로는 성립하지 않습니다.**

| 항목 | LATEST(internal) | TEST_A |
|---|---|---|
| 해제선 | `ARM_RELEASE_USD = 5000` (별도 상수) | `flU >= -thrU * 0.5` = **3000 하드코딩** |
| arm 대기 | `WAIT_MIN = 0` | `T_LHEDGE_ARM_WAIT_MIN = 60` |
| 레스큐·VScan·전개 해제선 게이트 | 3개 전부 있음 | **3개 전부 없음** |
| L11 배율 | 5.3 | 3.3 |

이 상태로 A/B를 돌리면 **다른 EA를 재는 것**입니다. 검증하려면 TEST_A에도 같은 61줄이 들어가야 합니다.

## D. 전파 작업 — 가장 게으른 형태

`LOCKED == LATEST − 7/31축 + 소성블록` 이 실측으로 확인됐습니다. LOCKED vs LATEST diff 11 hunk 중 **구조적 차이는 hunk 1(락업 소성) 단 하나**이고, 나머지 10개가 전부 7/30+7/31 축입니다.

**LOCKED — 14줄 (권고)**

라인 61줄을 손으로 옮기지 말고, **LATEST를 통짜 복사한 뒤 799~814행(16줄)만 LOCKED의 14줄 소성 블록으로 교체**하십시오. 1 hunk, 앵커 유일(`input group "④  기능 스위치"`).

라인 이식보다 짧고, **드리프트가 구조적으로 0**이 됩니다. 지금 LOCKED가 7/31 축을 통째로 놓친 것 자체가 라인 이식 방식의 실패 사례입니다.

**앤트가드 — 61줄 추가 + 8줄 치환** (통짜 재빌드 불필요)

AG의 LHEDGE 구역은 LOCKED와 바이트 동일이고, 필요 심볼이 전부 있으며 뚜껑갈이 리네임 충돌 0입니다. 앵커 11개 전부 `count == 1` 확인했습니다.

| # | AG 라인 | 작업 | 줄수 |
|---|---|---|---|
| 1 | 1220 `LHEDGE_ARM_LOTS` 뒤 | 상수 블록 삽입 | +8 |
| 2 | 1239 `FIRST_REARM_USD` | 5.0 → 0.0 | 치환 |
| 3 | 1241 `CD2_SEC` | 1800 → 7200 | 치환 |
| 4 | 1246 `REARM_USD` | 5 → 0.0 | 치환 |
| 5 | 1317 `PROG_MULT_L11` | 3.3 → 5.3 | 치환 |
| 6 | 3912 랏 각인 | `ARM_USD<=0.005 &&` 선행 | 치환 |
| 7 | 16972 RescueEnter | 치환 + 레스큐 게이트 | 치환 +7 |
| 8 | 17035 `retraceBlock` 뒤 | VScan 게이트 | +8 |
| 9 | 18115 `for(int sd...)` 앞 | arm 4단 블록 | +21 |
| 10 | 18207~18208 | 0값 가드 2개 | 치환 ×2 |
| 11 | 18214 `REDEPLOY_MAX` 앞 | 전개 해제선 게이트 | +9 |
| | | **합계** | **+61 / 치환 8** |

**TEST_A — 동일 61줄** (T_ 접두 input 체계라 상수명만 `T_` 로 승격, +2 input)

**순서 권고:** ①LATEST 무변경 → ②LOCKED = LATEST 재생성(14줄) → ③AG 61줄 → ④TEST_A 61줄.
GOLD_INDEX §4-8이 AG 적용을 "TEST A/B 후"로 게이트하고 있으니 AG를 먼저 태울지는 사장님 판단입니다.
